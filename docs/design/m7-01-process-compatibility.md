# M7-01 process compatibility assessment

Research baseline: main ff9d6b5a4554822783a0694369954499eb5f5a8e, 30 October 2026. Scope is research and planning only. [Current roadmap](../roadmap.md) assigns generic processes to M7 and optional potential-bug analysis to M8.

## Conclusion

Reuse Flow, Node, Edge, EntryPoint and SourceReference. No required class, method, language, framework or AST exists in the schema. Existing graph ownership, hierarchy, canonical Markdown links, offline search and HTML packaging can serve both input modes.

Two real integration gaps require work: prompt evidence must become an actual cited input artifact under the existing file-reference rules, and the output selector/bundle resolver must implement the new location policy while preserving old bundles. Repository-only Skill routing and software-specific UI/template language also need small changes. There is no evidence for a second model, participant entity, new node category, rendering engine or general state framework.

## Proposed prompt evidence profile

Recommendation for M7-02 approval: retain the developer-supplied process description as actual input evidence under architecture/evidence/, outside the canonical Markdown corpus. Retain later clarification answers as attributed input evidence without inventing intermediate statements. Keep the documented input distinct from generated explanation; never cite generated prose as proof of itself. Do not turn omissions into claimed facts. Repository analysis continues to cite real code/configuration instead of replacing it with a prompt summary.

Keep two filesystem roles distinct: the location-selection root chooses where output goes; the evidence-containment root is passed to the existing Builder as repositoryRoot and bounds SourceReference paths. For repository analysis the latter remains the actual project root. For default prompt output, recommend the current working directory as that evidence root, so a reference could point to docs/architecture/evidence/request.md. Symbol stays absent; line numbers refer to the actual captured text. This is proposed evidence reuse, not a new field or virtual prompt:// protocol.

An explicit output outside the source/input root needs a deliberate evidence-root decision: current validators prohibit evidence escaping the selected root. Recommend using the explicit output bundle as the evidence root for prompt-only input, passing it through the existing repositoryRoot parameter, so the same captured file is referenced as evidence/request.md. This does not change which current directory selected the default location or repository analysis's actual source root. Do not silently widen repository evidence access. Test both roots; confirm this behavior in M7-02 before implementation.

Evidence stored inside a prompt bundle is compatible with current M1/M4 full builds but not M6-02 apply, which explicitly rejects source/output overlap. Do not delete that guard to make prompt incremental updates appear to work. Explicit external repository output is already supported by M4 generation but not by M6-02 targeted apply, which requires a contained bundle. Preserve and report that existing limit rather than expanding transaction scope in this refactor. Existing safe Builder/rebuild publication still applies to prompt full builds; preserving manual Markdown during subsequent prompt regeneration requires a separate baseline/ownership decision and must block unsafe overwrite.

Participants remain prose. No actor registry, role enum, approvals engine, execution simulator or swimlane renderer is justified by the approved requirements. A missing essential start or branch outcome warrants a focused question; an unspecified minor detail warrants omission. Async delivery and substep expansion must never be inferred merely from nearby descriptions.

## Output policy and layout gap

The approved default chooses project root for repository mode and current directory for prompt mode, then existing docs/, existing doc/, or new docs/, in that order. An explicit output directory bypasses this selection. Recommend retaining its existing meaning as the final bundle directory, without appending an unexpected second architecture/ level. Handle file collisions, unwritable paths and unsafe symlinks explicitly; never silently fall back or overwrite source/user files.

The policy changes location selection. The product examples also suggest a flatter package than the existing Builder accepts. Recommended target to confirm before M7-03:

```text
<selected docs or doc>/architecture/
  index.md
  flows/*.md
  diagrams/architecture.json
  evidence/request.md       # prompt input only, when that evidence exists
  architecture.html
```

Keep one connected graph envelope, including reusable detail and cross-flow relationships; diagrams/ does not imply splitting Flow objects into incompatible documents. Keep architecture.json as the recognized filename. JSON docs links such as flows/onboarding.md stay relative to the selected Markdown root. Source citations must be rebased from actual document locations. No duplicate authoritative Markdown copy should be maintained merely to satisfy old path assumptions.

Legacy bundles remain readable as architecture.json + sibling docs/index.md and docs/flows/*.md. A small deterministic resolver must distinguish legacy versus flat layouts without guessing between conflicting corpora. M6's hardcoded graph/docs paths, document block preservation and index inventory must be included in compatibility work; a Builder-only change is insufficient. Preserve old behavior until the shared path decision is approved and tested.

## Research checks and limits

A disposable authored onboarding probe used unchanged schema 1.0.0, validateDocumentation, prepareBuild and generateHTML. It had no Git repository, classes, methods or source symbols. A UTF-8 developer-description text file supported operation/decision/terminal Nodes and branch edges with unknown mode. With the current legacy bundle layout it produced zero validation diagnostics and one 135958-byte in-memory standalone HTML string. Replacing the evidence path with prompt://conversation was rejected as missing/unreadable evidence.

Probe driver/result are private research scratch files at /private/tmp/pflow-m7-01-probe.mjs and /private/tmp/pflow-m7-01-probe-result.json. This is a structural/build compatibility check, not a new prompt analyzer, product feature, AI accuracy evaluation or browser verification. It does not demonstrate that the new output layout, root policy or dual-input Skill exists today.

No runtime, schema, Viewer, Builder, Skill implementation, fixture or test file changes belong to M7-01. Existing M6 tests remain the regression baseline; the proposed tests above belong to their approved future implementation tasks.

## Proposed M7 tasks and next decision

1. **M7-02 — Dual-input orchestration and prompt evidence.** Confirm evidence capture, root handling and semantic reuse, then add the prompt path to existing orchestration. Retain the current supported bundle layout for this first small step. Validate a described hierarchy and branches without fabricated responsibility or order.
2. **M7-03 — Output policy and compatible bundle resolution.** Implement the approved directory precedence and agreed flat/legacy resolution together with affected M4/M6 path assumptions. Preserve explicit overrides, canonical links, source safety and old outputs. No alternate Builder.
3. **M7-04 — Generic presentation and templates.** Change software-specific copy while preserving read-only diagram/search/inspection behavior and repository details. Avoid mode-based public fields and a UI redesign.
4. **M7-05 — Unified compatibility evaluation.** Exercise repository, onboarding and deployment input through the same pipeline, including non-Git prompt directories, supported hierarchy, ambiguity, malicious text, location selection, safe rebuild and the existing M1–M6 suites. Separate structural, AI-source accuracy and offline-browser evidence.

Recommend approval of M7-02 with the file-backed evidence proposal first. Do not start it in this task. Schema versioning is needed only if a later approved requirement actually cannot fit existing fields or semantics; this research found no such structural requirement for the stated examples. M8 remains entirely deferred as specified in the roadmap.
